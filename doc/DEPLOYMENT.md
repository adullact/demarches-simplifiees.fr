# Deployment documentation

This is the documentation for deploying and upgrading a production instance of demarche-numerique.

demarche-numerique is a standard Rails app, and can be deployed using standard methods (PaaS, Docker, bare-metal, etc.) This guide documents the deployment on a bare-metal server.

## 1. Pre-requisites

demarche-numerique requires several external services and dependencies to run. These dependencies can be provided all on the same host, or on different hosts or machines.

### Hosting infrastructure

demarche-numerique can scale from a single-server hosting all services, to a large swarm of purpose-specific servers.

For small and middle-sized instances (around up to 1 million files), you can start with:
- A single server/VM for the PostgreSQL database,
- A single server/VM (~4 cores, ~16 Go RAM) for all the rest: application, web server, async jobs processor, Redis, weasyprint, etc.

For instances with more than about 1 million files, you can add more servers/VMs with specific roles (like a dedicated async jobs processor, several web application servers, etc.)

> [!TIP]
> Deploying a staging instance is a good idea. It allows testing upgrades and migrations beforehand.
>
> The staging instance can run all services on the same server/VM, including the database.

### Services

To run demarche-numerique, you will need the following services:

- **PostgreSQL** (version >= 15). Postgres is used as the database for all application data. Only a single instance and a single database is required (there is no sharding as of now).
- **Redis** (version >= 7.0). Redis is used as an application-wide cache, as a shared lock mechanism, and as the backend for asynchronous job processing.
	
	> [!NOTE]
	> Technically, demarche-numerique can run without Redis (by using the local filesystem as a cache, and `delayed_job` as the async jobs backend.)
	>
	> This is strongly discouraged in production, as it prevents some important performance optimizations[^1].
- **An email provider**. Emails are sent for enrolement, account management, notifications, etc.
    The application can use either:
	- An `smtp` email service,
	- A properly-configured `sendmail`,
	- A [Brevo](https://www.brevo.com) account.
	
	> [!TIP]
	> Email reception is critical for the users.
	>
	> We strongly recommend a well-configured email server with SPF, DKIM and DMARC, an IP address with a good reputation, a dedicated IP if possible, and closely monitoring email errors.
- **An Object Storage**. The Object Storage is used to store files sent by the users (like supporting documents), the admins (like procedure notices), or generated by the application (like attestations).
	
	Files can be stored to either:
	
	- any S3-compatible Object Storage (Scaleway, OpenStack, Garage, etc.),
	- the local filesystem of the application (not recommended in production).
	
	As this storage will contain <abbr title="Personnally Identifiable Informations">PII</abbr>, it should be well secured (and at least encrypted at rest).

	It must allow direct HTTP requests by the browser on the app domain (you may need to configure CORS for this, see [Object Storage and Data Encryption](doc/object-storage-and-data-encryption.md)).
- **WeasyprintServer**. WeasyPrint is a locally-running tool used to convert HTML attestations to PDF. [`weasyprint_server`](https://github.com/demarche-numerique/weasyprint_server) is a small Python shim around WeasyPrint to expose a network API.

    See the instructions in the [project Readme](https://github.com/demarche-numerique/weasyprint_server/blob/main/README.md) to install the relevant Debian package.
- **(Optional) `ds_proxy`**. [ds_proxy](https://github.com/demarche-numerique/ds_proxy) encrypts file transferts between the Object Storage and the application.
	
	Set it up only if at-rest encryption of the files does not meet your security requirements, and you need to add an extra layer of security by encrypting the content of the files themselves during transfer and storage.

- **(Optional) Matomo**. [Matomo](https://matomo.org/) can be used to track usage statistics.
- **(Optional) Sentry**. [Sentry](https://sentry.io) (as a SaaS or self-hosted) can be used to monitor application exceptions.
- **(Optional) Skylight**. [Skylight](https://www.skylight.io/) can be used to monitor the application performances.

### API Keys

- **"API Entreprise" API Key**. [API Entreprise](https://entreprise.api.gouv.fr/) is used to retrieve a wide range of company data from a SIRET code. Use the API Entreprise website to [submit a request](https://entreprise.api.gouv.fr/) and obtain an API key.
- **(Optional) Signaturit/Universign API Key**. [Signaturit](https://www.signaturit.com) (formerly Universign) can be used to sign timestamped audit logs of the application activity, for compliance purpose.

## 2. Preparing the server

### 2.1 Installing binary dependencies

The web application and the asynchronous jobs require some binary dependencies.

- **System packages**

	```shell
    apt install zip unzip libjemalloc-dev libpq-dev libicu-dev postgis libvips-dev gsfonts poppler-utils
    ```

    > [!TIP]
    > At this stage you may also want to install the [compilation packages required for building Ruby and Ruby extensions](https://github.com/rbenv/ruby-build/wiki#ubuntudebianmint).
- **Bun**. [Bun](https://bun.sh/) is the JavaScript execution environment that compiles and packages the assets. It is required to pre-build the assets before starting the application.
	
	Once the assets are built, bun is not used at runtime.
	
	> [!TIP]
	> See https://bun.sh/docs/installation for setup instructions.
- **(Optional) ClamAV antivirus**. [ClamAV](https://www.clamav.net/) can be used to scan attachments sent by the users for known viruses.

### 2.2 Creating the `ds` user

This is the user account under which demarche-numerique will run:

```shell
sudo adduser --disabled-password ds
```

### 2.3 Setting up the database

You now need to create a database for the application.

Open the Postgres prompt:

```shell
sudo -u postgres psql
```

Then in the prompt execute:

```sql
CREATE USER ds;
ALTER USER ds WITH SUPERUSER; -- to create extensions; can be disabled later
CREATE DATABASE ds_production OWNER ds;
GRANT ALL PRIVILEGES ON DATABASE ds_production TO ds;
```

## 3. Deploying demarche-numerique.fr

First, switch to the `ds` user:

```shell
sudo su - ds
```

### 3.1 Copying the code

Use `git` to download the release you want to deploy:

```shell
git clone https://github.com/demarche-numerique/demarche-numerique.fr /var/www/ds && cd /var/www/ds
git checkout <release_tag>
```

> [!NOTE]
> If you prefer to use a tarball, source archives are available from the [Releases page](https://github.com/demarche-numerique/demarche-numerique.fr/releases/).

### 3.2 Installing the proper Ruby version

[Ruby](https://www.ruby-lang.org) runs the main application code. Use the Ruby version specified in the repository's `.ruby-version` file.

[`rbenv`](https://github.com/rbenv/rbenv) is the preferred way to install ruby and manage ruby versions (but any method of installing Ruby with the correct version will do).

First install `rbenv` and `ruby-build`:
```shell
curl -fsSL https://github.com/rbenv/rbenv-installer/raw/HEAD/bin/rbenv-installer | bash
```

Then build and install the proper ruby version:
```shell
rbenv install $(cat .ruby-version) -- --with-jemalloc --enable-yjit
```

### 3.3 Installing dependencies

Install the required Ruby and Javascript dependencies with:

```shell
bundle config deployment 'true'
bundle config without 'development test'
bundle install
bun install
```

### 3.4 Configuring with env vars

The application uses environment variables for its configuration. 
The easiest way to start is to load the environment variables from the file system:

```shell
cat config/env.example config/env.example.optional > .env.production
```

Then review and edit the `.env.production` file with the proper settings.

> [!NOTE]
> The `.env.production` file is not mandatory: environment variables can be managed in the way you want.
> Just ensure that all these environment variables (including `RAILS_ENV`) are defined before running any `rails` command.

## 3.5 Bootstrapping the app

Now that the Ruby code is properly configured, we are going to create the database, precompile the assets, and schedule recurrent tasks.

```shell
RAILS_ENV=production bin/rails db:schema:load
RAILS_ENV=production bin/rails assets:precompile
RAILS_ENV=production bin/rails jobs:schedule
```

### 3.6 Setting up the systemd services

Copy the systemd service templates from the `doc/dist` directory:

```
cp doc/dist/ds-*.service /etc/systemd/system/
[[ -d "/opt/weasyprint" ]] || rm /etc/systemd/system/ds-weasyprint.service
```

If you deviated from the defaults at any point, check that the username and paths are correct:

```
$EDITOR /etc/systemd/system/ds-*.service
```

Finally, start and enable the new systemd services:

```
systemctl daemon-reload
systemctl enable --now ds-web ds-sidekiq
```

From now:
- The services will automatically start at boot,
- The web server is accessible on port 8080.

### 3.8 Setting up a reverse proxy

It is recommanded to use a dedicated web server (like `nginx` or `caddy`) as a proxy between the internet and the application.

In that case, the dedicated web server must also be configured to serve static files in the `/var/www/ds/public/` directory.

(If you prefer exposing `puma` directly to the internet, define the `RAILS_SERVE_STATIC_FILES` environment variable, and Rails will serve static files itself – at the cost of some performance.)

## 4. Customizing text and images

A handful of directories (`/app/custom_views/`, `/config/custom_locales`) may contain git-ignored files used to customize the instance. These files should be backed up before deploying, and restored afterwards[^2].

For more details, see [Customization.md](doc/customization.md).

## 5. Administrating and troubleshooting

### 5.1 Manager and super-admin

Super-admin users can access the Manager at `https://ds.example.org/super_admins/sign_in`.

This administration tool allows them allows to explore database records, and perform some actions for troubleshooting specific situations:

- Accessing the procedures,
- Accessing individual files (without the actual user-provided data),
- Accessing the asynchronous jobs dashboards,
- Running Maintainance tasks,
- Enabling or disabling feature flags,
- Displaying announcements to end users,
- Import or export CSV data.

To list, create and super-admins, see the related tasks with `RAILS_ENV=production bin/rails --tasks superadmin`.

## Footnotes

[^1]: Here is one of the reasons Redis is required in production:

    An indexation job is enqued after each edit to a file, to recompute the file search terms. When Redis is used as the caching backend, these indexations can be debounced, and use only a single job per 5 mn time slice. But without Redis, indexation jobs are not debounced, and may clog the async jobs runner. ([Source](https://github.com/demarche-numerique/demarche-numerique.fr/releases/tag/2024-05-27-01))

[^2]: For instance, among the possible backup/restore strategies, a custom git repository storing the content of those two directories may be a good choice.
